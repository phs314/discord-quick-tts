# 한 번에 함께 저장하는 것은 애그리거트 하나다

ADR 0024 로 업무 규칙이 애그리거트로 들어가면서, 서비스는 애그리거트를 꺼내 메서드를 부르고 다시 저장하는 모양이 됐습니다. 그런데 저장하는 방법은 정해진 것이 없었습니다.

- 한 유스케이스가 애그리거트를 몇 개까지 고쳐도 되는지 정해져 있지 않았습니다. 기기 등록은 연결 코드(`Pairing`)를 지우고 기기(`Device`)를 만들고, 허용 목록 처음 채우기는 `AllowedGuild` 를 여러 개 넣습니다.
- 허용 목록 처음 채우기는 `@Transactional` 로 묶여 있었는데, 같은 메서드의 다른 갈래에서 디스코드 서버 나가기(되돌릴 수 없는 외부 호출)를 그 트랜잭션 안에서 했습니다.
- DB 의 애그리거트를 읽어 고쳐 다시 저장하는 곳이 아직 없어서, 두 요청이 같은 애그리거트를 동시에 고치면 어떻게 되는지도 정해져 있지 않았습니다.
- 저장소 포트 이름도 `AllowedGuildPort.add` 처럼 ADR 0027 규칙 3번(`save` / `find...` / `delete...`)에서 벗어나 있었습니다.

## 결정

1. **한 번에 함께 저장하는(같이 성공하고 같이 실패하는) 것은 애그리거트 하나입니다.** 애그리거트가 곧 일관성 경계입니다. 애그리거트 안의 규칙은 애그리거트가 지키고, 애그리거트 사이는 순서대로 따로 저장합니다.
2. **예외는 같은 종류를 한꺼번에 만들거나 지울 때뿐입니다.** 이때 서비스가 반복문으로 하나씩 저장하지 않고, 포트 메서드 하나(`saveAll`, `deleteAllByOwner`)로 넘깁니다. ~~어댑터가 SQL 문장 하나로 처리해서 DB 가 알아서 모두 되돌리게 합니다.~~ ADR 0033 으로 어댑터는 유스케이스의 트랜잭션 안에서 한 줄씩 쓰고, 하나라도 실패하면 그 트랜잭션이 모두 되돌립니다. 서로의 값을 보고 판단하는 경우는 예외가 아닙니다.
3. **다른 애그리거트도 바뀌어야 하면 한 번에 묶지 않습니다.**
   - 같은 컨텍스트 안이면 서비스가 차례로 따로 저장합니다. 이때 뒤의 저장이 실패해도 남는 상태가 안전한 순서로 합니다. 기기 등록은 연결 코드를 먼저 지우고 기기를 저장합니다. 기기 저장이 실패하면 연결 코드만 버려지고, 사용자는 `/연결` 을 다시 하면 됩니다. 순서를 거꾸로 하면 같은 코드로 기기를 두 개 만들 수 있습니다.
   - 다른 컨텍스트면 ADR 0026 의 도메인 이벤트로 이어서, 받는 쪽이 커밋 뒤에 자기 애그리거트를 고칩니다.
4. **DB 애그리거트 저장소 포트의 기본 모양은 `findById`, `save`, `delete`** 입니다. 그 밖의 동작은 이름에 드러냅니다(`findByOwner`, `saveIfAbsent`, `saveAll`, `deleteAllByOwner`). `save` 는 새것이면 넣고, 있으면 고칩니다. 지금은 고쳐 쓰는 DB 애그리거트가 없어서 넣기만 합니다.
5. **고쳐 쓰는 DB 애그리거트가 처음 생기면 `version` 으로 낙관적 잠금을 겁니다.** 애그리거트에 `version` 필드를 두고, 저장은 `update ... where id = ? and version = ?` 로 합니다. 0행이면 다른 요청이 먼저 고친 것이므로 `ErrorKind.CONFLICT` 예외를 던집니다. 지금은 규칙만 두고, 그런 애그리거트가 생길 때(예: 사용자 설정) 처음 붙입니다.
6. **메모리 애그리거트는 포트가 잠금을 맡습니다.** `BotSeatPort.withLockedSeat` 는 디스코드 서버마다 잠그고 그 안에서 고치게 하고, `PairingPort.findAndDelete` 는 꺼내면서 지워 두 번 쓰지 못하게 합니다. 잠금 안에서 외부 호출(봇을 음성 채널에 들이기)을 할 때는 외부 호출이 성공한 뒤에 애그리거트를 고칩니다(`join` 뒤에 `sitIn`).

- ~~`EnforceGuildAllowlistService.leaveAllNotAllowed` 는 처음 채울 때 `saveAll` 을 부르고 `@Transactional` 을 뗐습니다.~~ 이제 디스코드 서버 나가기가 트랜잭션 안에서 일어나지 않습니다. ~~일부만 들어가지 않는지는 서비스 대신 저장소 테스트(`JdbcAllowedGuildRepositoryTest`)가 H2 와 MySQL 양쪽에서 확인하고, 스프링 문맥을 띄우던 `EnforceGuildAllowlistTransactionTest` 는 없앴습니다.~~ ADR 0033 으로 처음 채우기는 `@Transactional` 을 붙인 `fillIfEmpty` 로 떼고, 나가기는 트랜잭션이 없는 `leaveAllNotAllowed` 에 남겼습니다. `GuildAllowlistTransactionTest` 를 다시 두어 둘 다 확인합니다.

- 이 규칙들은 ArchUnit 으로 잡기 어려워서 리뷰로 지킵니다.

## 고르지 않은 것

- 한 유스케이스는 언제나 애그리거트 하나만 고치기: 기기 모두 해제(N개 삭제)를 기기마다 따로 지워야 하고, 중간에 실패하면 일부만 지워집니다. 기기 등록처럼 연결 코드를 쓰고 기기를 만드는 흐름도 이벤트로 쪼개야 해서, 얻는 것보다 복잡해집니다.
- 이유만 적으면 둘 이상 고쳐도 되게 하기: 이유는 언제든 붙일 수 있어서 결국 규칙이 없는 것과 같아집니다. 허용하는 경우를 2번, 3번으로 정해 둡니다.
- 처음 채우기를 서비스의 `@Transactional` 로 계속 묶기: 같은 메서드에서 디스코드 서버 나가기가 트랜잭션 안에 들어가고, 트랜잭션이 실제로 되돌려지는지 보려면 스프링 문맥을 띄운 테스트가 따로 필요합니다. 한꺼번에 넣기는 저장소가 맡는 편이 `deleteAllByOwner` 와도 같은 모양입니다. (ADR 0033 에서 처음 채우기를 나가기와 다른 메서드로 나눠 `@Transactional` 을 다시 붙였습니다. 한꺼번에 넣기는 지금도 저장소의 `saveAll` 이 맡습니다.)
- 지금 바로 모든 테이블에 `version` 붙이기: 고쳐 쓰는 DB 애그리거트가 없어서 쓰이지 않는 열과 코드만 늘어납니다.
- 비관적 잠금(`select ... for update`): 막을 수는 있지만 트랜잭션 동안 줄을 잡고 있어야 하고, H2 와 MySQL 에서 똑같이 동작하는지 따로 확인해야 합니다. 이 봇의 동시 수정은 드물어서, 부딪혔을 때 다시 하게 하는 낙관적 잠금이 맞습니다.
