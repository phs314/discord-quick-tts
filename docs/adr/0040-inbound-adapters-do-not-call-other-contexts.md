# 인바운드 어댑터는 다른 컨텍스트의 유스케이스를 부르지 않고, 다른 컨텍스트 소식은 공개 이벤트로 받는다

- 상태: 채택
- 날짜: 2026-10-19

ADR 0026 은 다른 컨텍스트를 부르는 자리를 둘로 열었습니다. 요청을 받으면서 바로 필요한 것은 **인바운드 어댑터**가 상대의 입력 포트를 부르고, 서비스가 일하는 도중에 필요한 것은 내 출력 포트를 `adapter/out/<상대>` 가 구현해 상대의 입력 포트를 부릅니다. 첫째 길은 `QuickChatController` 가 device 의 `AuthenticateDeviceUseCase` 로 기기 토큰의 주인을 묻던 것 때문에 있었는데, ADR 0031 에서 인증을 device 의 시큐리티 필터로 옮기며 쓰는 곳이 없어졌습니다. 길은 그대로 남아서, 컨텍스트 지도에 짝을 하나 넣으면 컨트롤러나 디스코드 리스너가 다른 컨텍스트의 유스케이스를 바로 불러도 빌드가 통과했습니다.

그렇게 되면 그 어댑터는 두 컨텍스트에 걸칩니다. 상대의 `...Command`, `...Dto`, 예외를 알게 되어 상대가 바뀌면 내 어댑터도 고쳐야 하고, 두 컨텍스트의 일을 이어 붙이는 순서(무엇을 먼저 하고 실패하면 어떻게 하는지)라는 업무 판단이 서비스가 아닌 어댑터에 들어갑니다.

## 결정

- **다른 컨텍스트를 부르는 자리는 `adapter/out/<상대>` 하나입니다.** 내 서비스가 내 말로 된 출력 포트(`...Port`)를 부르고, 그 포트를 구현한 `adapter/out/<상대>/...Adapter` 가 상대의 입력 포트를 부르고 상대의 `...Dto` 를 내 값 객체로 바꿉니다(ADR 0026, ADR 0039).
- **인바운드 어댑터(웹 컨트롤러, 시큐리티 필터, 디스코드 리스너, 이벤트 리스너)는 자기 컨텍스트의 입력 포트만 부릅니다.** 요청 하나가 두 컨텍스트의 일을 필요로 하면, 내 유스케이스 하나를 부르고 그 서비스가 출력 포트로 상대를 부릅니다.
- **다른 컨텍스트에 "이 일이 끝났다" 고 알리는 것은 이벤트로 합니다.** 결과를 바로 받을 필요가 없고, 받는 쪽이 실패해도 내 일은 성공이어야 할 때입니다(ADR 0026, ADR 0033).
  - 보내는 쪽 서비스는 내 출력 포트(`...EventPort`)로 냅니다. 그 포트를 `adapter/out/event/...EventAdapter` 가 구현하고, 지금은 스프링 이벤트(`ApplicationEventPublisher`)로, 나중에 프로세스를 나누면 Kafka 같은 메시지 브로커로 보냅니다. 서비스는 어느 쪽인지 모릅니다.
  - 다른 컨텍스트가 받을 수 있는 이벤트는 보내는 쪽의 **공개 이벤트** record(`application/port/in/event/<과거형>Event`)입니다. 값은 원시 타입과 shared 의 값 객체만 담습니다. `domain/event` 의 도메인 이벤트는 컨텍스트 안에서만 쓰고, 다른 컨텍스트에 알려야 하면 `...EventAdapter` 가 공개 이벤트로 바꿔 냅니다. Kafka 로 옮기면 이 record 가 그대로 메시지 모양(JSON)이 됩니다.
  - 받는 쪽은 `adapter/in/event/...Listener` 가 공개 이벤트를 받아 **자기** 입력 포트를 부릅니다. 리스너가 아는 상대의 것은 공개 이벤트 하나뿐이고, 상대의 유스케이스는 부르지 않습니다. 컨텍스트 지도에는 받는 쪽 → 보내는 쪽으로 적습니다.
- `ArchitectureTest` 의 `contextsMeetOnlyAtPublicEntrances` 에서 `adapter.in` 을 부르는 자리로 허용하던 조건을 지웁니다. 계층 규칙이 다른 컨텍스트의 공개 입구를 쓰는 의존을 빼 주던 대상도 모든 어댑터(`..bot.*.adapter..`)에서 출력 어댑터(`..bot.*.adapter.out..`)로 좁힙니다.

## 결과

- 지금 코드는 바뀌지 않습니다. 컨텍스트 지도가 비어 있어 다른 컨텍스트를 부르는 곳이 없습니다.
- 다른 컨텍스트 기능을 쓰는 모양이 하나로 정해집니다. 서비스가 결과를 바로 받아야 하면 출력 포트와 `adapter/out/<상대>`, 끝났다고 알리기만 하면 되면 커밋 뒤 이벤트(ADR 0033)입니다.
- 컨텍스트 규칙은 `adapter.in.event` 가 지도에 있는 상대의 `application.port.in.event` 를 쓰는 것만 더 허용합니다. 계층 규칙도 그 의존을 뺍니다. 지금은 컨텍스트 사이 이벤트가 없어서 쓰는 곳은 없습니다. 같은 컨텍스트 안 이벤트(`GuildDisallowed`)는 지금처럼 도메인 이벤트를 그대로 씁니다.
- 받는 쪽이 보내는 쪽 이벤트 record 를 import 하므로 두 컨텍스트 사이에 코드 의존이 하나 남습니다. 대신 한 프로세스 안에서 스프링 이벤트로 바로 넘길 수 있습니다.
- 기기 토큰 인증(ADR 0031)은 그대로입니다. speech 의 요청이 device 의 필터를 거치지만, 필터는 device 의 인바운드 어댑터로 자기 컨텍스트의 유스케이스를 부르고, 둘을 잇는 것은 `config/SecurityConfig` 입니다. speech 는 shared 의 `DiscordUserId` 만 압니다.

## 고르지 않은 것

- 인바운드 어댑터에서 바로 부르기를 그대로 두기: 컨트롤러가 다른 컨텍스트 값을 잠깐 물어볼 때 파일 둘(출력 포트, 어댑터)이 줄지만, 어댑터가 두 컨텍스트에 걸치고 이어 붙이는 판단이 어댑터에 들어갑니다.
- 인바운드 어댑터 중 시큐리티 필터만 허용하기: 지금 인증은 필터가 자기 컨텍스트 것만 쓰므로 예외를 둘 곳이 없습니다.
- 받는 쪽이 이벤트 record 를 따로 두고 JSON 으로 받기: 컨텍스트 사이 코드 의존이 없어지지만, 한 프로세스 안에서도 직렬화나 메시지 브로커가 있어야 합니다. 프로세스를 나눌 때 다시 봅니다.
- 다른 컨텍스트가 `domain/event` 의 도메인 이벤트를 바로 받기: 파일은 하나 줄지만, 상대 도메인이 바뀔 때마다 받는 쪽도 고쳐야 합니다.
