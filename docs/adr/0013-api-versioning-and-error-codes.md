# API 경로에 버전을 붙이고, 오류는 코드로 구분한다

exe 를 다른 사람에게 나눠 주면 배포된 클라이언트와 봇 서버가 따로 업데이트됩니다. 그런데 API 경로에는 버전이 없었고(`/api/quick-chat`), 클라이언트는 오류를 HTTP 상태 코드로만 구분했습니다. 같은 400 이 "문장이 비었다" 와 "연결 코드가 틀렸다" 를 함께 뜻했고, 채널 정책을 넣을 때는 상태 코드가 모자라 409 와 423 을 나눠 써야 했습니다(ADR 0007). 오류 종류가 늘어날수록 상태 코드만으로는 버틸 수 없습니다.

## 결과

- 모든 경로는 `/api/v1` 아래에 둡니다(`QuickChatApi.VERSION_PREFIX`). 배포된 클라이언트가 깨지는 방식으로 요청·응답 모양을 바꿀 때만 `v2` 를 만들고, 그동안 `v1` 경로도 함께 살려 둡니다. 필드를 더하는 정도는 버전을 올리지 않습니다.
- 오류 응답은 지금처럼 ProblemDetail(RFC 9457)을 쓰고, 맨 위에 `code` 속성을 더합니다. 코드 값은 common 의 `ApiErrorCode` 에 모읍니다. common DTO 와 마찬가지로 클라이언트와 나누는 약속(Published Language)입니다.

  ```json
  { "status": 423, "title": "Locked", "detail": "...", "code": "voice-channel-in-use" }
  ```

- 클라이언트는 상태 코드가 아니라 `code` 로 안내 문구를 고릅니다. 모르는 코드나 코드가 없는 응답은 "봇 서버 오류 (HTTP n)" 로 보여 줍니다. 상태 코드는 지금처럼 뜻에 맞게 고르지만, 클라이언트가 기대는 것은 코드입니다.
- 이미 배포된 클라이언트가 알고 있으므로 코드 값은 바꾸거나 지우지 않고, 필요하면 새 코드를 더합니다.
- 기기 토큰 실패(401)도 빈 응답 대신 `device-unauthorized` 코드를 실은 ProblemDetail 로 돌려줍니다.
- 응답 본문은 성공이든 실패든 `ApiResponse` 같은 공통 봉투로 감싸지 않습니다. 성공은 그 응답 DTO 그대로, 실패는 ProblemDetail 그대로 둡니다. 클라이언트가 바라는 것은 실패 종류를 가리는 일이고, 그건 `code` 하나로 됩니다.
- 옛 경로(`/api/...`)는 남기지 않았습니다. 지금까지는 exe 가 클라이언트와 봇 서버를 함께 담아 늘 같이 바뀌었고, 다른 사람에게 나눠 준 적이 없기 때문입니다.
