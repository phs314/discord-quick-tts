# 디스코드 연결은 처음부터 ShardManager 로 만든다

- 상태: 채택
- 날짜: 2026-11-01

봇 서버는 `JDABuilder` 로 디스코드 게이트웨이 연결(JDA) 하나를 만들고, 어댑터마다 그 `JDA` 를 받아 썼습니다. 디스코드는 봇이 들어간 디스코드 서버가 2,500개를 넘으면 연결을 여러 개(샤드)로 나누지 않은 봇의 접속을 받지 않습니다. 그때 `JDA` 를 받던 어댑터를 모두 다시 고치는 것보다, 지금 작을 때 샤드를 묶는 `ShardManager` 로 시작하는 것이 쌉니다. 커질 디스코드 봇이 JDA 로 시작할 때 흔히 고르는 방식이기도 합니다.

## 결정

1. **`config/DiscordConfig` 는 `DefaultShardManagerBuilder` 로 `ShardManager` 빈을 만듭니다.** 인텐트, 캐시, 음성 설정(DAVE)은 전과 같습니다.
2. **샤드 수는 정하지 않고 디스코드가 권하는 대로 둡니다.** 지금은 1개이고, 디스코드 서버가 늘면 코드를 바꾸지 않고 늘어납니다. 봇 서버를 여러 대로 나눌 때 그 서버가 맡을 샤드(`setShards`)를 설정으로 받습니다.
3. **켜질 때는 모든 샤드가 준비될 때까지 기다립니다.** 디스코드는 샤드를 5초에 하나씩만 붙게 합니다. 봇 주인 받아 오기, 꺼져 있는 동안 초대된 서버 확인, 슬래시 명령 등록이 디스코드 서버 캐시가 다 차 있어야 하므로, 전에 `awaitReady` 로 기다리던 것을 샤드마다 합니다.
4. **어댑터는 `JDA` 대신 `ShardManager` 를 받습니다.** 디스코드 서버 찾기(`getGuildById`, `getGuilds`)와 봇 앱 정보(`retrieveApplicationInfo`)는 `ShardManager` 가 모든 샤드에서 찾아 줍니다. 이벤트 하나를 처리하는 곳에서 샤드 하나가 필요하면 이벤트의 `getJDA()` 를 씁니다(허용 목록 명령의 초대 링크).
5. **리스너는 모든 샤드에 등록하고, 슬래시 명령 목록은 한 샤드로 한 번만 보냅니다.** 슬래시 명령은 샤드가 아니라 봇 앱에 붙기 때문입니다.
6. **상태 확인은 모든 샤드가 `CONNECTED` 일 때만 `UP` 입니다.** 샤드 하나가 끊기면 그 샤드의 디스코드 서버에서는 봇이 말을 못 하기 때문입니다. 세부 내용에는 샤드마다 상태와 평균 게이트웨이 핑을 담습니다(웹으로는 전처럼 `UP`/`DOWN` 만 보입니다, ADR 0036).

## 결과

- 사용자가 보는 동작은 바뀌지 않습니다. 샤드가 1개라 연결도 전과 같은 하나입니다.
- API 통합 테스트는 `JDA` 대신 `ShardManager` 를 Mockito 빈 껍데기로 바꿉니다(ADR 0017).
- 음성 연결(`AudioManager`)은 디스코드 서버마다 그 서버를 맡은 샤드에 있으므로, `Guild` 를 찾은 뒤에 쓰는 지금 코드가 그대로 맞습니다.

## 고르지 않은 것

- 디스코드 서버가 늘 때 바꾸기: 그때는 `JDA` 를 받는 어댑터를 모두 고쳐야 하고, 2,500개에 가까워지면 서두르게 됩니다.
- 샤드 수를 설정 값으로 정해 두기: 디스코드가 권하는 수가 가장 흔한 기본값이고, 숫자를 정하면 서버가 늘 때 사람이 바꿔야 합니다.
- 켜질 때 기다리지 않고 샤드가 준비되는 대로 일하기: 켜질 때 하는 일을 샤드마다 준비 이벤트에 나눠 달아야 해서, 샤드가 하나인 지금 얻는 것이 없습니다.
