# 엔진이 만든 음성은 스프링 캐시(Caffeine)로 기억한다

- 상태: 채택
- 날짜: 2026-10-18

"ㅋㅋㅋ", "ㄱㄱ" 처럼 짧고 자주 쓰는 문장도 매번 비공식 TTS(ADR 0006)를 불렀습니다. 부르는 횟수가 많을수록 막힐 위험이 커지고, 매번 기다리는 만큼 읽기 시작도 늦어집니다.

## 결정

1. **스프링 캐시 추상화와 Caffeine 을 씁니다.** 캐시 이름은 `speech` 하나이고, 크기와 보관 시간은 `application.yml` 의 `spring.cache.caffeine.spec` 에 둡니다(500개, 마지막으로 쓴 뒤 하루).
2. **캐시는 TTS 어댑터 안, 엔진 하나를 부르는 자리에 둡니다.** `TtsEngine.synthesize` 에 `@Cacheable("speech")` 을 붙여서 키는 문장과 목소리입니다.
   - 엔진 하나의 결과를 기억하므로, Edge 가 실패해 Google 번역 목소리로 대신 읽은 음성이 Edge 목소리 자리에 남지 않습니다.
   - 실패는 기억하지 않으므로 다음 요청에서 다시 시도합니다.
   - 포트, 서비스, 도메인은 캐시를 모릅니다.
3. **캐시된 `Speech` 는 여러 요청이 함께 씁니다.** 음성 바이트는 읽기만 하고 고치지 않습니다.

## 결과

- 같은 목소리로 같은 문장을 다시 보내면 비공식 API 를 부르지 않고 바로 읽습니다.
- 메모리를 10MB 정도 더 씁니다(mp3 한 개가 20KB 안팎).
- 적중률은 `/actuator/metrics/cache.gets?tag=cache:speech` 로 봅니다(ADR 0036). `quicktts.tts.synthesis` 는 캐시에서 꺼낸 것도 함께 셉니다.
- 의존이 둘(캐시 스타터, Caffeine) 늘었습니다.

## 고르지 않은 것

- `MultiEngineSpeechSynthesizer` 에서 캐시하기: 엔진을 고르고 대신 읽는 결과까지 기억하게 되어, Edge 가 잠깐 실패했을 때 Google 번역 목소리가 하루 동안 남습니다.
- Caffeine 을 직접 들고 있는 코드: 스프링에서 흔한 `@Cacheable` 로 충분하고, 캐시 지표도 스프링 부트가 알아서 붙입니다.
- 디스크나 Redis 같은 바깥 캐시: 서버가 하나이고 다시 만들 수 있는 값이라 메모리로 충분합니다.
