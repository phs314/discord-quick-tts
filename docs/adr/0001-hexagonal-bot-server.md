# 봇 서버는 헥사고날 구조로 짓고 ArchUnit 으로 지킨다

봇 서버는 기능에 비해 작지만, 디스코드(JDA, LavaPlayer)와 TTS 엔진처럼 바뀌기 쉬운 바깥 것이 많습니다. 그래서 컨트롤러-서비스-리포지토리 계층 대신 도메인 / 애플리케이션(입력 포트, 출력 포트) / 어댑터로 나누는 헥사고날 구조와 DDD 용어를 쓰기로 했습니다. 바깥 것은 모두 어댑터에 두고, 애플리케이션은 포트로만 바깥과 이야기합니다.

규칙은 문서가 아니라 `ArchitectureTest`(ArchUnit)가 빌드 때마다 확인합니다. `domain` 과 `application` 은 스프링, JDA, LavaPlayer 를 모르고, 어댑터끼리는 서로 모릅니다.

## 결과

- 애플리케이션 서비스에는 `@Service` 같은 스프링 애너테이션이 없습니다. 포트와 어댑터는 `config/UseCaseConfig` 에서 `@Bean` 으로 이어 붙이므로, 유스케이스를 새로 만들면 여기에 빈을 하나 추가해야 합니다.
- 서비스 테스트는 스프링 없이 출력 포트의 가짜 구현으로 돌립니다.
- 클라이언트와 봇 서버가 함께 쓰는 요청 형식은 `common` 모듈에 두고, `desktop-client` 는 이 구조를 따르지 않습니다.
