# 데스크톱 입력창은 TestFX 로 화면 없이 띄워 테스트한다

- 상태: 채택
- 날짜: 2026-11-01

입력창은 이 앱에서 사람이 매번 쓰는 곳인데 지금까지 자동 테스트가 없었습니다. 한글 조합 커서·포커스처럼 윈도우에서 직접 써 봐야 알던 버그(PR #38)를 다시 손으로 확인하지 않도록, 입력창의 핵심 흐름을 CI 에서 지킵니다.

## 결정

1. **입력창 창(`QuickChatWindow`)을 `QuickTtsApp` 에서 떼어 냅니다.** 창 띄우기·닫기, Enter·Esc, 한글 조합 우회는 창이 맡고, 서버로 보내기·음성 채널 확인·트레이 알림은 앱이 맡습니다. 그래서 테스트는 서버·트레이·키보드 훅 없이 창만 띄웁니다.
2. **TestFX(`testfx-junit5`)로 창을 실제로 띄우고 키를 누릅니다.** 지키는 흐름은 단축키로 띄우면 바로 입력됨, 다시 누르면 닫힘, 한글 조합 중 커서와 점선, Enter 로 보내고 닫기, 빈 문장, 보내지 못한 문장 남기기, Esc 로 닫고 지우기입니다.
3. **화면은 JavaFX 에 들어 있는 Headless 플랫폼(`glass.platform=Headless`)을 씁니다.** 따로 Monocle 을 받지 않고, 리눅스 CI 와 개발 PC 모두에서 창이 뜨지 않습니다. 설정은 `apps/desktop-client/build.gradle.kts` 의 `test` 에 있습니다.
4. **한글 입력은 윈도우 한글 입력기가 보내는 이벤트(점선 표시, 커서 0)를 그대로 만들어 보냅니다.** 실제 입력기는 CI 에 없으므로 입력기가 보내는 모양을 흉내 냅니다.

## 결과

- `./gradlew build` 가 입력창 테스트까지 돕니다. 개발 PC 에서 돌려도 키보드나 포커스를 빼앗지 않습니다.
- Headless 플랫폼은 창 사이 포커스 이동을 흉내 내지 않아서 "다른 창을 누르면 닫힘" 은 테스트하지 못합니다. 창을 숨겼다 띄울 때 입력기를 다시 잇는 일(막대로 포커스를 옮겼다 돌리기)과 윈도우 foreground 처리(`WindowsForeground`)도 실제 윈도우에서만 확인됩니다.

## 고르지 않은 것

- Monocle(`org.testfx:openjfx-monocle`): 예전에 TestFX 를 화면 없이 돌리던 흔한 방법이지만, JavaFX 26 에는 Headless 플랫폼이 들어 있어 의존성을 하나 더 둘 까닭이 없습니다.
- CI 에 가상 화면(Xvfb)을 띄우기: 실제 GTK 창이 떠서 더 진짜에 가깝지만 CI 설정이 늘고, 개발 PC 에서 돌리면 창이 떠 입력을 빼앗습니다.
- `QuickTtsApp` 을 통째로 띄워 테스트하기: 연결 코드 창, 설정 파일, 트레이, 키보드 훅까지 가짜로 바꿔야 해서, 지키고 싶은 입력창 흐름보다 준비가 훨씬 커집니다.
