# 음성은 임시 파일 없이 메모리에서 바로 재생한다

- 상태: 채택
- 날짜: 2026-10-22

TTS 엔진이 준 음성 바이트를 시스템 임시 폴더(`quicktts`)에 파일로 쓰고, LavaPlayer 의 로컬 파일 소스가 그 파일을 다시 읽어 재생했습니다. 음성은 이미 메모리에 있고 캐시(ADR 0037)도 바이트로 들고 있는데 디스크를 한 번 거쳤습니다. 그래서 딸린 코드와 문제가 생겼습니다.

- 켜질 때 1시간 넘은 파일 지우기, 재생이 끝나거나 큐를 비울 때 파일 지우기, 파일 쓰기 실패용 `UncheckedIOException`(ADR 0025 의 예외 표).
- 파일 읽기가 LavaPlayer 의 다른 스레드에서 끝나서, 디스코드 서버마다 순서를 맞추려고 `loadItemOrdered` 를 썼습니다. 읽기가 봇 자리 잠금(ADR 0014) 밖에서 끝나므로, 나가기 직전에 넣은 문장이 큐를 비운 **뒤에** 들어갈 수 있었습니다.
- 음성 바이트가 깨져 있으면 불러오기 실패 로그만 남고 보낸 사람은 202 를 받았습니다. 소리가 안 나도 알 길이 없었습니다.

이 ADR 은 ADR 0014 결과의 "그 안에서 임시 음성 파일도 쓰지만" 과 ADR 0025 예외 표의 임시 파일 `UncheckedIOException` 줄을 바꿉니다.

## 결정

1. `SpeechPlayerDiscordAdapter.play` 는 음성 바이트에서 바로 LavaPlayer 트랙을 만들어 그 디스코드 서버의 재생 순서에 넣습니다. LavaPlayer 의 파일 소스가 안에서 하는 일(스트림 → `MediaContainerDetection` 으로 형식 알아내기 → 그 형식의 트랙 만들기)을 그대로 하고, 스트림만 파일 대신 바이트 배열(`ByteArraySeekableInputStream`)로 줍니다. 모두 LavaPlayer 공개 API 입니다.
2. 트랙은 부른 자리(봇 자리 잠금 안)에서 바로 큐에 들어갑니다. `loadItemOrdered` 와 로컬 파일 소스 등록은 쓰지 않습니다.
3. 형식을 알아내지 못하면 `SpeechSynthesisException`(502, `speech-synthesis-failed`)으로 알립니다. 엔진이 읽을 수 없는 음성을 준 것이라 "음성을 만들지 못했다" 와 같은 실패로 봅니다.
4. `Speech.fileExtension` 은 이름은 그대로 두고 형식 힌트로만 씁니다.

## 결과

- 디스크를 쓰지 않습니다. 임시 폴더, 남은 파일 청소, 파일 지우기 코드와 그 테스트가 없어졌습니다.
- 같은 디스코드 서버에서 자리 잡기, 채널 들어가기, 재생 순서 넣기가 정말로 한 번에 하나씩 끝납니다. 나가기와 문장 넣기가 엇갈려 옛 문장이 다음 채널에서 읽히는 일이 없습니다.
- 깨진 음성은 보낸 사람에게 "음성을 만들지 못했습니다" 로 알려집니다. 이때 봇은 이미 채널에 들어가 자리를 잡은 뒤이고, 그건 실제 상태와 맞습니다.
- 기다리는 문장마다 음성 바이트(mp3 20KB 안팎)를 메모리에 듭니다. 캐시가 이미 같은 바이트를 들고 있어서 늘어나는 건 거의 없습니다.
- 형식 알아내기를 LavaPlayer 스레드 대신 요청 스레드에서 합니다. 앞 몇 바이트만 보는 일이라 짧습니다.

## 고르지 않은 것

- 임시 파일 그대로 두고 경쟁 조건만 고치기: 딸린 코드는 그대로 남고, 파일 읽기가 잠금 밖에서 끝나는 구조라 다른 엇갈림을 계속 따로 막아야 합니다.
- `AudioSourceManager` 를 새로 만들어 `loadItem` 으로 넣기: 바이트를 문자열 주소로 넘길 방법이 따로 필요하고, 불러오기가 다시 다른 스레드에서 끝납니다. 우리는 트랙을 저장했다 되살리는 기능(`encodeTrack`)을 쓰지 않으므로 소스 매니저가 필요 없습니다.
- Lavalink(따로 띄우는 음성 서버): 음성을 URL 로 가져가므로 봇 서버가 음성을 HTTP 로 내놓아야 하고 서버가 하나 더 생깁니다. exe 에 넣기도 어렵습니다.
