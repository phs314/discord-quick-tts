# 핵심 약속 "빠름" 을 quick chat 지표 두 개로 잰다

- 상태: 채택
- 날짜: 2026-11-01

이 제품이 사용자에게 하는 약속은 "단축키로 친 문장이 바로 들린다" 입니다. 지금 지표(ADR 0036)는 TTS 엔진이 음성을 만드는 데 걸린 시간만 잽니다. 그 앞뒤로 채널 찾기, 봇 음성 상태 잠금, 채널 들어가기가 있고, 재생 순서에서 앞 문장을 기다리는 시간도 있어서, 엔진이 빨라도 사용자는 늦게 들을 수 있습니다. 그래서 사용자가 느끼는 시간을 두 구간으로 나눠 잽니다.

## 결정

1. **`quicktts.quickchat.speak`: quick chat 을 받고 재생 순서에 넣기까지.** 봇 서버 안에서 걸린 시간 전부입니다(문장 다듬기, 채널 찾기, 음성 만들기, 채널 들어가기, 순서에 넣기). 받는 쪽 어댑터인 `QuickChatController` 가 잽니다.
   - `outcome`: `success`, `failure`. "빠름" 은 `success` 만 봅니다.
   - `error`: 실패하면 오류 코드(`ApiErrorCode` 값, 예: `author-not-in-voice-channel`), 성공이면 `none`, 예상하지 못한 실패는 `unexpected`. 값이 정해진 몇 개뿐이라 태그로 둡니다.
2. **`quicktts.speech.queue.wait`: 재생 순서에 들어와서 재생을 시작하기까지.** 같은 디스코드 서버에서 앞 문장이 읽히는 동안 기다린 시간입니다. 재생하는 쪽 어댑터의 `GuildSpeechQueue` 가 트랙에 넣은 시각을 달아 두고, 재생을 시작할 때 잽니다. 재생하지 못하고 버려진 문장(봇이 나감)은 세지 않습니다. 디스코드 서버별 태그는 달지 않습니다. 서버 수만큼 지표가 늘어나기 때문입니다.
3. **두 지표는 중간값과 95% 값을 서버에서 계산해 둡니다** (`management.metrics.distribution.percentiles`). 아직 그래프 화면(Prometheus, Grafana)이 없으므로 `/actuator/metrics/quicktts.quickchat.speak.percentile` 에서 바로 봅니다.
4. **지표는 ADR 0036 처럼 어댑터에서만 셉니다.** 포트, 서비스, 도메인은 지표를 모릅니다.

## 결과

- 두 값을 더하면 사용자가 문장을 보내고 소리가 나기 시작하기까지의 시간에 가깝습니다. 데스크톱 클라이언트에서 봇 서버까지 오는 시간과 디스코드가 소리를 보내는 시간은 빠집니다.
- 느려지면 먼저 `quicktts.quickchat.speak` 와 `quicktts.tts.synthesis` 를 견줘, 엔진 탓인지 그 밖의 단계 탓인지 가릅니다.
- 몇 초 안에 들려야 하는지(목표 값)는 아직 정하지 않습니다. 배포해서 실제 값을 본 뒤에 정합니다.

## 고르지 않은 것

- 스프링 부트가 기본으로 재는 `http.server.requests` 만 보기: 같은 구간을 재지만 인증 필터, JSON 읽기까지 섞이고 이름이 제품 약속을 말하지 않습니다. 오류 코드로 나눠 볼 수도 없습니다.
- 서비스에서 재기: 지표는 기술 관심사라 어댑터에 둡니다 (ADR 0036).
- 받은 시각을 포트로 넘겨 받고 나서 재생 시작까지 한 지표로 재기: 지표 때문에 포트와 명령에 시각이 끼어듭니다. 두 구간으로 나누면 어디가 느린지도 바로 보입니다.
- `@Timed` 어노테이션: AOP 의존과 설정이 더 들고, 오류 코드 태그를 달 수 없습니다. 지금 TTS 지표와 같은 `Timer.Sample` 방식으로 맞춥니다.
